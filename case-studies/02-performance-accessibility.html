Context

  • Mobile-first user journeys with heavy authenticated flows and some third-party SDKs.
  • Goal: measurable Core Web Vitals improvements and an a11y baseline that blocks regressions in CI.
  • Constraint: anonymized, multi-environment setup with strict data-protection requirements.

Performance testing process

Lighthouse CI (lab budgets)

  • Track CWV deltas per PR and nightly; fail build on budget breaches (LCP/CLS/INP proxies, perf score).
  • Artifacts: JSON + HTML reports uploaded to CI; trend chart maintained in a shared dashboard.

k6 (API & page-level scenarios)

  1. Scope & endpoints: auth, search/listing, details, and save/submit operations mapped from the test plan (see “Performance test cases”).
  2. Scenarios & stages: smoke (sanity), baseline (steady), ramp (load), and brief spike (resilience) with realistic RPS per endpoint.
  3. Thresholds: p(95) latency, error-rate, and checks% (e.g., p(95)<500ms, errors < 1%, checks >= 99%). Threshold failures = CI fail.
  4. Data & auth: token bootstrap per VU, seeded users, idempotent writes, and isolated test tenants.
  5. Outputs: CI console summary + JSON summary; optional InfluxDB/Grafana for trend charts.
  6. Gating: PRs run smoke/baseline; nightly runs include ramp/spike and publish trend.
k6 scenario sketch (illustrative) 
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
    checks: ['rate>=0.99'],
  },
  scenarios: {
    baseline: {
      executor: 'constant-arrival-rate',
      rate: 20, // requests/second target
      timeUnit: '1s',
      duration: '5m',
      preAllocatedVUs: 20,
      maxVUs: 50,
    },
    ramp: {
      executor: 'ramping-arrival-rate',
      startRate: 10,
      timeUnit: '1s',
      stages: [
        { target: 50, duration: '5m' },
        { target: 80, duration: '5m' },
        { target: 0,  duration: '2m' },
      ],
      preAllocatedVUs: 20,
      maxVUs: 120,
    },
  },
};

export default function () {
  const res = http.get(__ENV.BASE_URL + '/api/v1/search?q=abc', { headers: { Authorization: `Bearer ${__ENV.TOKEN}` }});
  check(res, { 'status 200': r => r.status === 200 });
  sleep(1);
}

Accessibility testing process

I combine automated rules with manual UX checks. The checklist below (used across all projects) maps to WCAG 2.1 AA.

Automated checks (CI)

  • axe-core scan on key templates (public pages + authenticated flows).
  • HTML validity & landmark roles (header/main/nav/footer) verified.
  • Color contrast thresholds (text & UI components) evaluated.

Manual checks (keyboard & screen reader)

  • Keyboard-only: focus visible, logical order, trap-free modals, escape/close behavior.
  • Forms: label associations, error summary/aria-live announcements, descriptive buttons.
  • Screen reader smoke (NVDA/VoiceOver): headings hierarchy, control names, alt text, status updates.
Accessibility checklist (anonymized sample)
  • Page has a single <h1>; headings follow a logical order.
  • All actionable elements have accessible names (buttons/links/icons).
  • Form fields have labels; error messages are programmatically associated.
  • Keyboard can open/close modals and move focus back to the trigger.
  • Focus state is visible and not obscured across themes.
  • Images have meaningful alt or alt="" when decorative.
  • Color contrast ≥ 4.5:1 (text) and ≥ 3:1 (UI components) where applicable.
  • Live regions/alerts announce async updates (e.g., form success).
  • Skip-to-content link present and functional.

CI/CD integration

  • Lighthouse CI on PR + nightly with budgets; artifacts stored.
  • axe automated checks on PR; manual checks documented per release.
  • k6 smoke on PR; baseline + ramp/spike nightly; thresholds gate merges.
